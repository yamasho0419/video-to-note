# 動画 → note 予約投稿パイプライン

動画1本ごとに決まった工程を通し、note.com の予約投稿まで進める。
ルールの本文は `references/` にあり、このファイルは「何をどの順で、どう確かめながら進めるか」だけを書く。

## 守ること(理由つき)

- **即時公開はしない。** 予約投稿までにとどめる。最終的に人が読んで止められる余地を残すため
- **公開済み・予約済みの記事の本文は書き換えない。** 読者がもう見ている、または予約本文は draft_save で変わらないため
- **`.secrets/` の中身をスキル・ログ・報告に書かない**
- **分からないことは推測で埋めない。** `human_review` に入れて、その記事は予約しない
- note.com への書き込み(下書き作成・更新・予約)は、ユーザーがその種類の書き込みを許可している範囲で行う。
  初めて扱うチャンネルや、いつもと違う書き込み(既存下書きの作り直しなど)は先に確認する

## 0. チャンネルを決める

チャンネルは環境変数 `NOTE_CHANNEL`(既定 `sample`)。設定は `channels/{名前}/`:

| ファイル | 中身 |
|---|---|
| `channel.json` | 管理表・記事・画像などの置き場所、Cookie の場所、投稿の時間枠、フッターのリンク規則 |
| `voice.md` | 話者・一人称・定型の自己紹介・文体の型・CTA の方針 |
| `footer.md` | 結びのあとに一字一句そのまま入れるフッター |
| `glossary.md` | 字幕の誤変換を直すときの正しい表記 |

新しいチャンネルを足すときは `references/add_channel.md`。以下のコマンドは、別チャンネルなら先頭に `NOTE_CHANNEL={名前}` を付ける。

## 1. 対象を決める

| 依頼 | 対象 |
|---|---|
| 「12番」「この URL」 | その1本(URL だけなら管理表で番号を引く。表に無ければ 2. で追加) |
| 「10〜20」 | 範囲の全行 |
| 「未処理を全部」「続きから」 | `python3 scripts/pipeline_status.py --pending` に出る行 |
| 「この動画を追加して」 | `python3 scripts/add_video.py <URL>...` で表の末尾に足してから処理 |

## 2. 状態を確かめる(毎回ここから)

```bash
python3 scripts/pipeline_status.py 10-20            # ○=済み ×=未 旧=旧手順で済ませた扱い
python3 scripts/pipeline_status.py 10-20 --remote   # note.com の予約状態も読む(読み取りのみ)
```

「次の工程」から始める。済んだ工程はやり直さない(やり直したいと言われたときだけ戻る)。
注記(`- 〜`)が出ていたら先に片付ける。例:「meta が旧パスにある」→ `git mv` で `articles/meta/` へ移す。
「表は下書き☑だが meta が無い」→ note.com に下書きがあるか確かめるまで新規作成しない(重複を作らないため)。

## 3. 1本ごとの工程

| # | 工程 | やること | 済みの判定 |
|---|---|---|---|
| 1 | fetch | `bash scripts/prep_video.sh <番号> <短縮名>` | 文字起こし・00_thumbnail.jpg |
| 2 | title | 題名を作り `python3 scripts/channel.py set <番号> note記事の名前 "<題名>"` | 表の列が空でない |
| 3 | write | スクショ選び+執筆 → `{articles}/{番号2桁}_{短縮名}.md` | 記事md がある |
| 4 | lint | `python3 scripts/lint_article.py <番号>` | ERROR 0 |
| 5 | critique | 添削+別エージェントのファクトチェック → `critiques/{video_id}.md` | 状態ブロックに critiqued |
| 6 | eye | 全画像の目チェックと差し替え | 状態ブロックに eye_checked |
| 7 | push | `python3 scripts/note_push.py <番号>` | meta の pushed_sha が記事mdと一致 |
| 8 | reserve | `python3 scripts/note_schedule.py <番号>` → 確かめて `--commit` | 表の予約投稿完了☑ |

### 1. fetch
短縮名は動画の内容を表すローマ字の小文字とアンダースコア(例: `git_basics`、`sql_index`)。
日本語は使わない(シェルでの扱いやすさのため)。
記事md・文字起こしmd・画像フォルダの名前はどれも `{番号2桁}_{短縮名}` にそろえる。
字幕が無い動画は `WHISPER_PY`(mlx-whisper の入った python)を指定する。無ければ失敗として報告する。
yt-dlp が返す動画タイトルが表の「元の動画の名前」と大きく違うときは、別の動画を掴んでいる可能性があるので human_review。
yt-dlp が失敗したら1回だけ再試行する。

### 2. title
`references/writing_rules.md` §7 の5ポイントで作る。表の「note記事の名前」が既に埋まっていればそれを使う。
記事md の1行目もこの題名にする(予約のときは表の列の題名が使われる)。

### 3. write
先に読むもの: `references/writing_rules.md`(全部)、チャンネルの `voice.md`・`glossary.md`・`footer.md`、文字起こし、概要欄。
スクショは `references/eye_check.md` §1 の手順で、書きながら節ごとに選ぶ(あとで目チェックが楽になる)。
テロップに出た固有名詞・数字を、字幕の誤変換の補正に使う。確かめられないものは human_review の候補として控える。
最後にフッター(`footer.md` をそのまま)を付け、writing_rules.md §8 の自己チェックをする。

### 4. lint
ERROR は直す。WARN は1件ずつ見る(機械の目安なので、自然に読める文を無理に割らない)。

### 5. critique
`references/critique.md` の手順。ファクトチェックは `references/fact_check.md` のひな形で、
**このセッションでも執筆したサブエージェントでもない、新しいエージェント**に頼む。

### 6. eye
`references/eye_check.md` §2〜§4。全画像を Read で見る。差し替えたら状態ブロックに `eye_checked` を書く。

### 7. push
`note_push.py` は、新規なら下書き作成・画像・見出し画像・meta・表の noteのURL/下書き☑まで行う。
既存なら note.com の状態を確かめてから更新する。次のときは止まり「要人間」を出すので、human_review に移して次の動画へ進む:
予約済み・公開済み/note.com 側だけ手で直されている/表に URL があるのに meta が無い/保存後の題名が違う。
旧手順で作った下書き(meta に remote_sha が無い)も止まる。`get_note()` で note.com 側の本文を読み、
ローカルの記事mdと文章が同じ(手直しが無い)と確かめられたら `--force-remote` を付けて送る。違えば human_review。
目チェックで差し替えた画像は `--reupload=03_a.jpg,...` を付ける。

### 8. reserve
`human_review` が空のときだけ進む。
1. `python3 scripts/note_schedule.py <番号>`(dry-run)で、題名(表の「note記事の名前」)と日時を確かめる
2. 投稿予定日時が空・過去なら、`channel.json` の slots から次の空き枠を表に書いて、報告に明記する
3. `python3 scripts/note_schedule.py <番号> --commit` → 予約後の検証が通ると表の「予約投稿完了」が☑になる

## 4. 複数本のとき

- **ローカルの工程(1〜6)は1本につき1つのサブエージェントに任せ、同時に3本まで**走らせる
  (ユーザーが本数を指定したらそれに従う)。各サブエージェントには、番号・このファイルのパス・
  「note.com と管理表の『noteのURL・下書き・予約』列には触らない(題名列の記入はよい)」「最後に状態と human_review を返す」を伝える
- ファクトチェックのエージェントは、執筆したサブエージェントとは別に立てる(5. の理由)
- **note.com への書き込み(7・8)と管理表のチェック列の更新は、メインのセッションが1本ずつ順に**行う。
  書き手を1つにして、二重作成と表の書き換えの競合を防ぐため
- 1本が失敗しても止めない。失敗した工程と理由を控えて次へ進む
- `NoteAuthError` が出たら、その時点で note.com への書き込みを全部やめる。ローカルの工程だけ続け、報告に1行「Cookie の取り直しが必要」と書く
- 途中で止まっても、もう一度 `pipeline_status.py` から始めれば続きになる

## 5. 人間に回すもの(human_review)

次に当たったら自分で決めず、`critiques/{video_id}.md` の `human_review` に1行で書き、その記事は予約しない。

- テロップでも確かめられない固有名詞・数字(誤変換の疑い)、動画の中で食い違う数字
- 定型の自己紹介と、撮影時点の経歴の食い違い
- voice.md で「human_review に回す」とされている判断(例: 本文中の問い合わせへの誘導)
- 半目の差し替え候補がテロップ違いのコマしか無い/文脈から浮いた画像の代わりが無い
- ファクトチェックの「高」で、削るか元に戻すかでは解消できないもの
- `note_push.py` が止まった理由(予約済み・手直しあり・meta 無し・題名の不一致)

## 6. 最後の報告

次の3つの表で返す(1本だけでも同じ形)。下書きURLは `https://editor.note.com/notes/{note_key}/edit/`。

```
## 成功(予約まで完了)
| 番号 | 題名 | 予約日時 | 下書きURL | 備考(差し替えた画像の数など) |

## 失敗
| 番号 | 止まった工程 | 理由 | 次にやること |

## 要人間確認
| 番号 | 確認してほしいこと | 判断材料 | 下書きURL |
```

日時を自動で埋めた記事、lint の WARN を理由つきで残した記事は備考に書く。
Cookie の期限など、エラーが出ていないことは書かない。

# 添削の進め方と記録の書式

添削は「書いた記事を、内容を変えずに読みやすくする」工程。新しく書き直す工程ではない。
基準は `writing_rules.md` とチャンネルの `voice.md` だけを使い、ここで独自のルールを作らない。

## 手順

1. `python3 scripts/lint_article.py <番号>` を実行する。ERROR は必ず直す。WARN は1件ずつ見て、直すか理由を残す
   (WARN は機械の目安なので、自然に読める文を無理に割らない)
2. 記事を通読する。観点は writing_rules.md の §2〜§5(事実・型・見出し・読みやすさ)
3. 画像を本文の登場順に全部 Read で開く。観点は §6(置き場所・文脈・過不足)。目チェックは `eye_check.md` の工程で行う
4. 改善点を「引用 → 問題 → 修正例」でまとめ、記事mdに反映する。
   執筆と同じエージェントが続けて添削するときは、記事を頭から通読し直し、執筆中の自己修正とは別に、通読で見つけた点を記録する
5. `fact_check.md` の手順で別エージェントにファクトチェックを頼み、確かめられた指摘だけ反映する
6. lint をもう一度通す
7. `critiques/{video_id}.md` を下の書式で書く(既にあれば、先頭の状態ブロックを更新し、本文の末尾に追記する)

画像の追加・削除で代わりの画像が無いとき、本文中のチャンネル固有の判断(voice.md に「human_review に回す」とあるもの)は、
自分で決めずに `human_review` に入れる。

## critiques/{video_id}.md の書式

先頭の状態ブロックはパイプラインの状態判定(`pipeline_status.py`)が読む。キー名を変えない。

```markdown
<!-- pipeline
critiqued: 2026-10-21
eye_checked: 2026-10-21 (12枚中2枚差し替え)
human_review: []
-->
# 添削結果: {note記事の名前}

対象: `{記事mdのパス}`(管理表 {番号}番)

## 総評
(2〜3文。今の読みやすさと、直して一番効いた点)

## 良い点
- (引用つき)

## 改善点と反映内容
1. 【高】(引用)→(問題)→(修正)
2. 【中】…

## 画像まわりの評価
- N枚とも本文と対応 / 置き場所を直した画像
- 目チェック: N枚中M枚が半開き。(差し替えた画像: 元の時刻→新しい時刻。対象外と判断した画像と理由)

## 結びと導線の評価
(直接相談の表現が無いか、呼びかけで終わっているか、フッターが固定文面と同じか)

## 別エージェントによるファクトチェック
| 指摘 | 重大度 | 対応 |
|---|---|---|

## 要人間確認
(human_review に入れた項目ごとに、何を決めてほしいか・判断材料・下書きURL。無ければ「なし」)
```

`human_review` は1項目を短い文字列にして、カンマで区切る。例:
`human_review: [15_message.jpg がテロップ違いのコマしか無い, 本文中の問い合わせ誘導の一文を残すか]`
人間が判断して片付いたら項目を消す。空 `[]` になると、パイプラインは予約へ進める。
